## 三、P0 致命问题（必须第一时间修，否则"决策大脑"自相矛盾）

### P0-1 ❶ 服务端缺关键依赖 `https-proxy-agent` → 全新部署 AI 与定时分析直接崩溃

**文件**：`server/package.json`、`server/routes/ai.js:9`、`server/cron.js:41`

**问题**：
`server/routes/ai.js` 第 9 行 `const { HttpsProxyAgent } = require("https-proxy-agent");` 和 `server/cron.js` 第 41 行都**模块顶层 require** 了 `https-proxy-agent`，但 `server/package.json` 的 `dependencies` 只有：
```
cors, dotenv, express, node-cron, pg
```
**没有 `https-proxy-agent`**。由于是顶层 `require`，一旦在干净环境 `npm install` 后 `node index.js`，会在加载 `routes/ai.js`（`index.js:47`）时抛 `MODULE_NOT_FOUND`，**整个服务端启动失败** → AI 中转、定时抓取、LLM 分析全部不可用。
（你本机能跑，大概率是因为父目录或全局 `node_modules` 里恰好有该包，但**不可复现、CI/新机器必崩**。）

**修改指令**：
1. 编辑 `server/package.json`，`dependencies` 增加：
   ```json
   "https-proxy-agent": "^7.1.0"
   ```
2. 把 `ai.js` 与 `cron.js` 里的 `require("https-proxy-agent")` 改为**惰性加载**（用到一个模块里定义一次，并 try/catch 容错），即使代理未安装也只降级不走代理而非崩溃：
   ```js
   let HttpsProxyAgent = null;
   try { ({ HttpsProxyAgent } = require("https-proxy-agent")); } catch { HttpsProxyAgent = null; }
   // 使用处：agent = HttpsProxyAgent ? new HttpsProxyAgent(url) : null
   ```
3. 抽出公共 `server/lib/httpProxy.js`，`ai.js` 与 `cron.js` 共用，消除两份重复的 `postJSON`/`callLLM`（见 P1-9）。

**验收**：在干净目录 `rm -rf node_modules && npm install && npm start` 能正常监听 8080 且 `/api/ai/config` 返回 200。

### P0-3 ❸「阶段判定」六套口径打架——决策大脑的精神分裂（影响你"启动/分歧"诉求）

**文件**：`App.tsx:170 judgeMainlineStage`、`themeScore.ts:165 stageMap`、`mainline.ts:150 兜底`、`emotionCycle.ts computeEmotionCycle`、`MainlineRanking.tsx:10 inferStage`、`llmNewsIntelligence.ts cycleStage`

**问题**：同一个"主线阶段"概念，全仓库有**至少 6 套互不一致的定义**：

| 来源 | 词表 | 判定维度 |
|---|---|---|
| `App.tsx judgeMainlineStage` | 启动/发酵/高潮/退潮/观察中 | 资金净占比(今/5d/10d) |
| `themeScore.ts stageMap` | 启动100/发酵80/观察50/高潮30/退潮0 | 仅映射分数 |
| `mainline.ts` 兜底 | 启动/发酵/高潮 | 连板高度(height) |
| `emotionCycle.ts` | 启动/主升/分歧/退潮/冰点 | 情绪分+涨停+炸板+溢价+晋级率 |
| `MainlineRanking.tsx inferStage` | 启动/主升/加速/分歧/退潮 | strengthScore |
| `llmNewsIntelligence cycleStage` | 启动/发酵/高潮/分歧/退潮 | LLM 文本判断 |

**后果**：同一条主线，作战卡显示"发酵期"、排行榜显示"主升"、情绪雷达显示"分歧"——游资会彻底懵。这是你诉求里"启动 vs 分歧"识别不靠谱的**根因**。

**修改指令**（建立单一权威阶段模型）：
1. 新建 `src/lib/stageModel.ts`，定义**唯一**词表与阈值：
   ```ts
   export type MainlineStage = "启动" | "发酵" | "高潮" | "分歧" | "退潮";
   export interface StageInput {
     ztCountToday:number; ztCountYesterday:number|null;
     heightToday:number; heightYesterday:number|null;
     blastedRateToday:number|null; blastedRatePrev:number|null;
     promotionRate:number|null; premiumAvg:number|null;
     mainNetPct:number; mainNet5dPct:number; boardPct:number;
   }
   export function classifyStage(input: StageInput): { stage: MainlineStage; reason: string; evidence: string[] }
   ```
   阈值建议（游资共识口径）：
   - **启动**：昨日无/少涨停，今日 ≥3 只首板且资金刚转正（mainNetPct>0 且 |mainNet5dPct|<1.5）
   - **发酵**：涨停环比↑、晋级率≥30%、梯队连续（首→二→三无断档）
   - **高潮**：高度见顶或环比不再升高 + 封板时间后移（10:30 后才封）+ 量价背离（boardPct≥7 但 mainNetPct 走弱）
   - **分歧**：炸板率环比↑≥10pp 或 涨停环比↓≥30% 或 晋级率骤降，但仍有龙头封死
   - **退潮**：龙头断板 + 跟风大面积溃散 + 资金连日净流出
2. 删除 `App.tsx judgeMainlineStage`、`MainlineRanking inferStage`、`mainline.ts` 兜底，**全部改为引用 `classifyStage`**。
3. `themeScore stageMap` 与 `emotionCycle` 改为消费同一份阶段输出（不再各自算）。
4. LLM 的 `cycleStage` 作为**交叉验证**，与规则 `classifyStage` 不一致时在 UI 标"⚠ AI与规则分歧"。

**验收**：同一主线在作战卡/排行榜/情绪卡显示**完全一致**的阶段词；`classifyStage` 有单测覆盖五态。

   ```ts
   export interface TrapInput {
     code:string; name:string;
     pct:number;                    // 涨幅
     sealFund:number;               // 封单(元)
     amount:number;                 // 成交额
     blastCount:number;             // 当日炸板次数 zbc

   ```
   诱多判定规则（游资实战）：

**验收**：对历史已知诱多样本（如某股涨停后次日跌停）回放，`detectTrap` 能在前一日封板时给出 isTrap=true。

## 四、决策大脑专项审查（你的核心诉求逐条拆解）

### 4.1「第一时间识别主线」——刷新节奏（已修正认知）

> **勘误（v2）**：初稿误称"60s 一刀切"。实际 `tradingSession.ts getCurrentSession()` **已是会话相位驱动**：集合竞价 09:15–09:29 = **30s**、盘中 09:30–11:30/13:00–15:00 = **60s**、盘后 = **300s**、午间休市/周末不刷。这点做得对，应予肯定。

**仍存在的真实缺口**：
1. **盘中 60s 仍偏慢**：游资的"第一时间"是分钟级甚至秒级，60s 抓不到"9:30:05 龙一直线封板、9:31 跟风梯队跟上"这种爆发瞬间。
2. **JSONP 并发≤2 导致单轮可能跑不完**：`refreshAll` 一次并发触发 8+ 个 `Promise.allSettled`，但 `jsonpQueue.ts` 全局并发上限只有 2（去重+退避重试）。盘中数据源多时，**一轮 60s 内可能根本抓不完所有数据**，等于"刷新了但没更新"。
3. **竞价数据没进主线引擎**：`auction.ts` 已接腾讯接口拿到竞价撮合，但只供 `AuctionBoard` 展示，**没回流到主线/强度分计算**，浪费了竞价这个最重要的"第一时间"信号源。

**修改指令**（P1-8）：
- 盘中对**涨停池 + 强势主线龙头 + 自选股**走独立 15~20s 高频小通道（只拉这几个轻量接口，不碰全量）；其余模块维持 60s。
- 竞价段（9:15–9:25）把 `auction.ts` 的竞价撮合结果**喂给主线引擎**做"竞价即封板"的早期主线识别。
- 评估放宽 `jsonpQueue` 并发上限（2→3~4）或对本地部署走 `server/routes/proxy`（fetch 不受 JSONP 并发限制）。

### 4.2「涨停梯队 + 跟涨梯队」——梯队完整，跟风粗糙

**现状**：
- `themeLadder.ts` 的梯队分层（首板/二板/三板+）和 `gapTiers` 断档检测**做得好**。
- 但 `mainlineScore.ts ladderScore` 只用了"三档是否存在"（全有=100），**没用断档位置和跟风厚度**。
- `BattlePlan.tsx:131` 的"跟风数" = `Math.max(0, ztCount - 1)`——**这是错的**。跟风梯队不是"涨停数减龙一"，而是"龙一/龙二/龙三之外、仍封板的承接票"，且要看它们的封板时间是否紧跟龙头（承接紧凑度）。

**修改指令**：
1. `themeLadder.ts` 增加"承接紧凑度"指标：龙一首封时间与跟风票首封时间的中位间隔（间隔越短梯队越实）。
2. `mainlineScore.ts` 梯队维度细化为：
   - 有断档（gapTiers 非空）→ 扣分；断档在"首→二"层（最致命）扣分加倍。
   - 跟风厚度：跟风票数 / 龙头数（健康主线 2~5 倍跟风）。
3. `BattlePlan.tsx` 修正跟风数计算，并展示"梯队结构图"（龙一▶龙二▶龙三▶跟风N）。

### 4.3「优中选优最终上车」——这块做得最好，微调即可

**现状**：`mainlineScore` 六维分 + `mainlineLLM` 精排 + 强催化注入（`mainlineCatalyst`）+ 完整度护栏——**这是全项目最强的环节**。
**唯一缺口**：
- `mainlineLLM.ts` 单次让 flash 同时做"识别真主线/脉冲 + 排序 + 置信度 + 确认龙头"，任务过重，flash 漏字段后走规则补齐（`parseLLMMainlineResult` 的 merged 逻辑）会**削弱 LLM 的排序价值**（被规则名次覆盖）。
- "上车"还缺一个**最终准入闸**：强度≥阈值 AND 阶段∈{启动,发酵} AND 无诱多 AND 闸门 mode≠empty AND 梯队无致命断档 → 才给"可上车"。
**修改指令**：见 P1-5（最终准入闸）。

### 4.4「仓位建议」——定性，没落地到金额/比例（你明确要的）

**现状**：
- `discipline.ts` 有总资金/单票上限/总仓位上限/当日新开仓上限/冷静期——**结构对**。
- `regimeGate.ts computeGate` 输出 `positionLimit`（百分比）。
- 但 `anomalyTier.ts` 的"重仓参与/轻仓参与"是**定性文案**，没和 discipline/gate 联动折算成具体金额或比例。
- 没有**分批建仓 / 加仓 / 止盈位**规则（首仓几成、突破加几成、冲高减几成）。

**修改指令**（P1-6 仓位定量化引擎）：
新建 `src/lib/positionSizing.ts`：
```ts
export interface PositionAdvice {
  mainline:string; action:"可上车"|"观望"|"禁止";
  suggestedPct:number;        // 建议仓位占总资金%(已折算闸门×强度×单票上限)
  tranches:{ trigger:string; pct:number }[];  // 分批:首仓/加仓/止盈减仓
  stopLoss:number|null;       // 止损%(基于纪律 settings)
  rationale:string;
}
```
公式骨架（示例）：
- `base = discipline.maxSinglePct`（单票上限，如 30%）
- `gateFactor = computeGate(...).factor`（如 0.7）
- `strengthDiscount = strengthScore>=80?1 : strengthScore>=60?0.6 : 0.3`
- `suggestedPct = round(base × gateFactor × strengthDiscount)`（如 30×0.7×1=21%）
- 分批：首仓 50% suggestedPct（启动/发酵期），强度上 80 且晋级 → 加 30%，偏离均线/炸板 → 减。
- 与 `discipline` 联动：若 suggestedPct 超 discipline 总仓位剩余 → 强制截断并提示。

### 4.5「离场信号」——只有主线级，没有个股级（你持仓是个股）

**现状**：`exitSignal.ts checkExitSignal` 是**主线维度**的（炸板率/涨停数/高度/资金环比）。但你真正需要的是"**我手里这只票什么时候跑**"。
**修改指令**（P1-7 个股级离场）：
新建 `src/lib/stockExit.ts`，输入持仓 + 实时分时，输出离场信号：
- 跌破分时均价线（需分时源，见 P1-8）
- 跌破持仓成本 `discipline.cost`（已有字段）
- 龙一/龙二熄火（所在主线龙头断板）→ 跟风票立即离场
- 封单快速消失（封单/成交比跌破阈值）
- 主力净占比由正转负且散户接盘（诱多，联动 trapDetector）
- 触发任一 → 弹红色离场预警 + 建议减仓比例。

## 六、LLM（Agnes 2.5 Flash）接入专项审查

### 6.1 优点（已做到位）
- Key 服务端托管、不入前端 bundle ✓

- JSON 幻觉护栏（board/code 白名单）✓

### 6.2 问题

**P1-9 多业务复用同一 task 名 → 缓存串任务、token 配置错配**
`llmSignals.ts scoreThemeNews`、`scoreStockNews` 和 `llmNewsIntelligence.ts generateDailyIntelligence` 都 `callAI("mainlineRank", ...)` 或 `callAI("stockJudge", ...)`，但：
- `ai.ts cacheKey = ai:cache:{task}:{date}:{hash(payload)}`——不同业务若 payload 不同 hash 不同**侥幸不串**，但语义上风险高，且 **token 配置被锁死在 task 名上**（`mainlineRank`=maxTokens1500/thinking=false，而情报分析实际需要更大 token）。
- `stockJudge` 是 `thinking:true / maxTokens:8000`，被情报分析复用导致**每次都开 thinking**，延迟高、配额消耗大。

**修改指令**：
1. 为每个业务建独立 task 枚举值（`themeNewsScore`/`stockNewsScore`/`dailyIntel`），在 `aiPrompts.ts TASK_CONFIG` 配对应参数；`server/routes/ai.js TASK_ALLOW` 同步加白名单。
2. cacheKey 增加"业务域"维度，杜绝跨业务命中。

**P1-10 单任务过重**
`mainlineRank` 让 flash 一次完成"识别真主线+脉冲+排序+置信度+确认龙头+逻辑+风险"。flash 在 ≤1500 token 输出下易漏字段。
**修改指令**：把"是否脉冲"和"排序"拆为两步，或精简 schema（去掉 caution 等可选字段，强制必填 rank/board/confidence）。
