# 第二轮详细修改指令——波段 AI 投研大脑
## 配合《第二轮审查报告-波段AI投研大脑-2026-08-15.md》使用

> 与第一轮指令不同：第一轮是"从0搭建能力"，第二轮的核心任务是**"把已经造好但孤立的能力，接管/替换掉用户实际会走的主路径"**，以及补齐少数仍然缺失的地基项。请按 P0 → P1 → P2 顺序执行，每完成一条在 PR/commit 中引用本文档编号。

---

## 〇、本轮验收基线（比第一轮更严格，因为地基已经存在）

不再问"有没有这个能力"，而是问：

1. 用户打开系统默认看到的那张"决策卡"，字段是否等于指令①1.2节"波段投研决策卡"规格（chain/fundamentals/timing/thesis/evidenceChain/provenance 全部展示，而不是散落在多个页签）？
2. 主 AI Agent（`agentTools.ts` 驱动的那一个）调用工具时，是否至少有一次机会读到产业链数据？
3. 深度调研功能是否能在**非开发者本机、无 Windows Python 环境**下正常工作？
4. 纪律教练检测出"处置效应/连续追高"后，下一次的建议仓位是否真的比不做检测时更低？
5. 一次波段买入建议生成后，30/60/90 天后是否有机制**主动**（不需要用户手动点）提醒复核？

验收方式：连续跟踪一只真实股票 30 个自然日，上述 5 点全部可用真实前端截图/日志证明，才算过关。

---

## 一、P0（本轮必须优先做，直接决定"新旧路径是否合并"）

### P0-1：主决策卡切换为"波段投研决策卡"，接入 `/api/decisions/swing`
- **现状**：`src/components/DecisionVerdictCard.tsx` 消费的是旧 ReAct Agent（`aiAgent.ts` + `agentTools.ts`）的打板结论；`/api/decisions/swing` 已经产出了完整的波段决策卡 JSON（`verdict/score/buyPoint/stopLossPct/targetPct/positionRange/holdingHorizonDays/reviewCycleDays/reasons/blocks/evidenceChain/invalidationConditions/signal`），但没有任何前端组件消费它（本轮抽查未发现调用方，`BattlePlan.tsx` 待确认，见 P0-1b）。
- **要求**：
  1. 新建 `src/components/SwingVerdictCard.tsx`（或明确复用 `BattlePlan.tsx`，先确认其是否已消费该接口——若是则只需补齐缺失字段展示，若否则新建），完整展示 `/api/decisions/swing` 返回的全部字段，尤其是**首屏必须可见**：`holdingHorizonDays`（持有多久）、`invalidationConditions`（什么情况算错）、`evidenceChain`（每条结论的证据来源，做成可展开列表，参考 `DecisionVerdictCard.tsx` 里"📋 证据链（点击展开）"的现有交互模式，直接复用即可）。
  2. 在应用主导航中，把这张新卡片提升为"个股详情页"的默认/首选决策卡，旧的五支柱打板卡降级为"日内战术参考"次级卡片（保留，但不再是首屏主结论）。
  3. 落库：确认 `/api/decisions/swing` 的裁决结果是否写入 `decision_log`/`decision_post`（供后续 `computePostHitrate` 对账）。若未写入，新增落库逻辑，`source` 字段区分标注为 `AI-Swing`，与旧的 `AI-Agent`/`规则投票` 区分开，避免污染现有命中率统计口径。

### P0-2：主 ReAct Agent 工具表接入产业链数据
- **现状**：`src/lib/agentTools.ts` 的 `getAgentTools()` 共 12 个工具，全部服务于超短打板决策（准入/仓位/离场/系统风险/因子健康等），无一查询产业链。
- **要求**：
  1. 新增工具 `getChainContext`（`kind: "data"`），`execute` 内部调用 `GET /api/chain/context?code=xxx`（复用 `server/routes/chain.js` 已有能力），返回 `chainName/nodeName/upstream/downstream/exposurePct/signals`。
  2. 在 `aiAgent.ts` 的主 system prompt 中明确要求：**判断"是否可上车"前，若个股已映射到某条产业链，必须先调用 `getChainContext`，并在 `reason` 字段中引用链上下游信息**（例如"该股为锂电中游材料环节，营收敞口23%，上游碳酸锂价格近20日+18%，符合成本传导逻辑"）。
  3. 验收：随机抽 10 只已在 `industry_chain_node_stock` 中有映射的个股，触发 AI 决策，检查 `reason`/`evidence` 字段是否引用了链信息，达标率需 ≥ 80%。

### P0-3：深度调研后端去 Windows 本地化，改为可生产部署
- **现状**：`server/routes/research.js` 通过 `execFile("C:/Python312/python.exe", [...])` 调用本机脚本，硬编码路径，无法在容器/Linux服务器/CI 环境运行。这是一个新发现的、比"思考深度"更基础的可用性缺陷。
- **要求**：
  1. 短期：把 Python 路径/脚本路径改为环境变量注入（`process.env.MX_PYTHON_BIN`、`process.env.MX_DATA_SCRIPT` 等），并在 `.env.example` 中补充说明，使其至少能在其他机器上通过配置跑起来。
  2. 中期：评估是否可以把 `mx-data`/`mx-search` 的核心检索能力改写为纯 Node.js HTTP 调用（如果它们底层也是调第三方 HTTP API 的话），去掉"必须有本机 Python 环境"这一强依赖，否则该功能在生产环境永远是"仅开发者可用"的残废功能。
  3. **Phase 3「行业博弈」改造**：`RESEARCH_SYSTEM` 的调研流程中，Phase 3 不应仅依赖 `mx-search` 开放式搜索，必须先调用 `GET /api/chain/context`（P0-2 同一个后端能力），把产业链结构化数据作为"行业博弈"分析的**第一手输入**，`mx-search` 降级为补充信息源。

### P0-4：纪律熔断真正生效（`behaviorCoach` → `decisionCore`）
- **现状**：`behaviorCoach.detectBehaviorBias` 能正确检测出处置效应/追高/频繁交易/不止损，但只在"纪律教练"面板展示文案，未反向影响 `decisionCore.js`/`decisionLayer.js` 的 `suggestedPositionPct`。
- **要求**：
  1. 在 `decisionLayer.js` 的 `composeDecision` 中，新增一步：调用（或注入）`behaviorCoach` 的最新检测结果，若存在 `severity: "alert"` 级别的行为偏差（如"不止损"占比>40%），对 `position.score`（建议仓位）打折（参考 `feedbackPenalty.js` 的 `scaled` 折算写法，逻辑可复用）。
  2. UI 侧在建议仓位旁明确标注"⚠ 已根据你近30日的止损纪律自动调低建议仓位"，让用户看到"纪律教练"真的在起作用，而不是自说自话。
  3. 验收：构造一个"连续3笔不止损"的模拟 `trade_ledger` 数据，验证同一只股票的建议仓位在有/无该行为记录时确实不同。

## 二、P1（次优先，完善已有能力的统计口径与覆盖面）

### P1-1：命中率对账补齐 T+20/T+60
- `decision_post` 表已有 `pnl_t20`/`pnl_t60` 字段（`db-migrations.js`），但 `decisionAttribution.ts` 的 `computePostHitrate` 及 UI 展示（`DecisionVerdictCard.tsx` "历史对账"）仍只用 T+5。
- 要求：新增 `aiPnlT20/rulePnlT20/aiPnlT60/rulePnlT60` 统计桶，UI 展示"近14日 vs 近60日"两组命中率，让波段仓（本来就该看月度表现）有对应的评价周期，而不是被短线的 T+5 口径误导。

### P1-2：用户画像注入 `/api/decisions/swing`
- `llmSwingDecision` 的 prompt 中未见画像信息，而旧决策卡（`DecisionVerdictCard.tsx`）已验证画像注入可行（`profileToPrompt`）。
- 要求：把 `profileToPrompt(profile)` 的输出作为 `llmSwingDecision` user prompt 的一段，明确告诉 AI"该用户历史上在什么情况下容易追高/止损不坚决"，并要求 AI 在 `reasons`/`blocks` 中针对性提示。

### P1-3：反馈归因选项在 UI 上补全
- `decision_feedback` 表已有 `attribution` 字段（服务端已支持任意字符串），但本轮未在前端组件中确认存在"产业链判断错/基本面判断错/择时判断错/数据本身错"四个可点选项（`DecisionActionPanel.tsx` 因文件截断未读取完整）。
- 要求：明确核对该反馈入口的 UI 实现，若只是自由文本框，需改造为"四选项 + 可选备注"的结构化输入，保证后续能统计"AI 在哪一层最容易犯错"（这是指令①P0-5 的原始验收要求，需要补齐）。

### P1-4：`industry_chain_event`（传导事件表）与推理复用
- 现状：产业链传导推理目前是"每次决策请求都让 LLM 重新推一次"，没有独立的、可复用的传导事件产出物。
- 要求：新增 `industry_chain_event` 表（字段参考指令①3.1节：`origin_node_id/title/summary/published_at/impact_path/impacted_nodes/confidence/model_generated`），新增一个独立的、低频触发的"产业链传导推理"任务（可复用 `aiPrompts.js` 里新增一个 `TASK_CONFIG` 条目，`thinking:true, maxTokens:6000`），由 `industry_chain_signal` 新数据触发（而不是每次个股请求触发），一次推理结果供该链上所有个股的 `/api/decisions/swing` 调用复用，显著降低 token 成本。

### P1-5：`SwingWarRoom`/`swingStage` 的持有周期延伸到"数月"
- 现状：`SwingWarRoom.tsx`/`swingStage.ts`/`swingDecision.ts` 明确定位"3天-1个月"，与最初"7天-数月"的目标存在时间尺度缺口（尤其"数月"级别，即60-180天的中长波段没有对应模型）。
- 要求：
  1. 在 `swingStage.ts` 基础上新增一个"周线级"阶段模型（输入周K线而非日K线，MA10周/MA20周），产出"中长波段位置"（对标指令①1.1节 L3 的"60-180天"档）。
  2. `swingDecision.ts` 的 `SwingDecisionInput` 增加基本面输入（当前完全没有 fundamentals 字段），至少接入 `fundamentalChecker.js` 的体检结果和 `catalysts`（催化日历），让"是否值得拿数月"这一判断不再只靠均线位置。

## 三、P2（地基补强，可与 P0/P1 并行安排资源）

### P2-1：`fundamentalChecker.js` 升级为趋势+同行对比
落实指令①4.1节：8期 ROE/毛利率/营收增速趋势线、同产业链节点/同申万行业估值分位对比、研报评级数量变化趋势。当前实现仍是单期阈值体检，未做任何时间序列或横向对比。

### P2-2：产业链覆盖面扩容
`src/shared/transmission-chain.js` 仍是 10 条，落实指令①3.3节，第一阶段至少扩到 40-50 条，优先补齐 AI 算力/机器人/创新药/军工低空经济/消费出海/数据要素/智能驾驶等指令①点名但缺失的方向。建议建立"连续多日成为资金/新闻焦点但不在库中 → 触发建链任务"的自动发现机制（而非人工一次性穷举）。

### P2-3：`catalyst_calendar` 独立成表
当前"财报窗口（earningsCalendar）+ 解禁（liftBan）"分散在两处，未形成指令①4.2节要求的统一 `catalyst_calendar` 表，且股权激励/回购计划进度/行业展会仍未覆盖。

### P2-4：产业协会数据源接入
`CommodityChain.tsx` 目前只用期货主连合约价格代理产业链景气度，指令①3.4节点名的乘联会/中汽协/光伏协会/半导体行业协会/统计局PMI/海关总署数据均未接入，需评估可抓取性后排期。

### P2-5：cron 与工程健康度专项复核
指令①2.1/2.2/2.3 提出的 cron 秒分混淆、`dateStr` 作用域、Agent 鉴权路径匹配问题，本轮静态审查**无法验证**是否已修复，建议：
1. 补充针对这三个历史 bug 的专项单元测试（若尚不存在），并在 CI 中固化；
2. 产出一份运行时的《数据管道健康报告》（cron 实际执行时间表 + `/api/ai/health` 快照 + `decision_feedback`/`logic_ledger` 当日新增条数），作为下一轮审查可核验的运行时证据（静态代码审查天然无法替代这份材料）。

## 四、执行顺序建议

```
第1周：P0-1（决策卡合并）+ P0-3（去Windows本地化，先做环境变量化）
第2周：P0-2（Agent接入产业链）+ P0-4（纪律熔断生效）
第3周：P1-1～P1-3（统计口径与UI补全）
第4周：P1-4～P1-5（传导事件表 + 中长波段周线模型）
第5周起：P2 全部（地基扩容类，可长期迭代，不阻塞主链路验收）
```

## 五、第三轮审查建议核验清单（供下一轮审查者直接使用）

1. 打开个股详情页，首屏看到的是否已是"波段投研决策卡"而不是旧五支柱打板卡？
2. 触发一次 AI 决策，`reason`/`evidence` 字段中是否出现产业链引用？
3. 在非 Windows/非开发者机器上（如 Linux 容器）触发"深度调研"，是否能正常返回结果？
4. 构造连续止损失败的模拟成交记录，同标的建议仓位前后是否有变化？
5. `decision_post` 表中 `pnl_t20`/`pnl_t60` 是否已有非空真实数据，UI 是否已展示对应周期命中率？
6. `industry_chain_event` 表是否存在且有真实记录？
7. `logic_ledger.next_review_at` 到期后，是否有主动推送（而非用户自己打开页面才看到）？

以上 7 项全部可核验为"是"，才能判定系统真正完成从"监控终端"到"产业链+波段+AI投研闭环"的转型。
