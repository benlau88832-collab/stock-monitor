## 一、总体结论（先说结论）

**判定：从"华而不实的监控终端"到"产业链+波段+AI投研闭环"——已完成实质性的地基工程，但尚未跑通"端到端使用同一套closed loop"，处于"半成品闭环"阶段，不能判定为"真实可用"。**

分层给出成熟度评估（0-5 分，5=达到指令①验收标准）：

| 层级 | 第一轮评分（报告①隐含） | 本轮评分 | 依据 |
|---|---|---|---|
| L1 产业景气层（板块级趋势/资金/催化打分） | 1/5 | **3.5/5** | `swingMainline.ts` 的 `scoreBoard`（趋势40%+资金35%+催化25%）已用真实板块指数K线+`fund_streak`历史+快讯催化，非纯静态表 |
| 产业链图谱（个股级映射+营收敞口） | 0.5/5（10条硬编码板块名） | **3/5** | 新增 `industry_chain / industry_chain_node / industry_chain_node_stock / industry_chain_signal` 四张表 + `chainDb.js` 真实拉取东财 F10 主营构成算 `exposure_pct`，并有 `/api/chain/context` 对外暴露；但链条数量仍只有 10 条，且主决策 Agent 未调用它（见下文症结7） |

| 假设监控（逻辑证伪机制） | 0/5（未提及） | **3.5/5** | 新增 `logic_ledger` 表（`thesis/catalysts/break_line/invalidation_conditions/review_cycle_days/next_review_at/status`）+ 前端"持仓逻辑台账"UI（`SwingWarRoom.tsx`），是本轮**最实的新增能力**，直接命中指令①"验收基线问题④"（假设有没有被证伪） |

**一句话总结**：团队确实做了一轮认真的"波段重构"（v9.138~v9.144），新增的数据表、纯函数模型、AI 综合研判接口在设计意图上**相当精准地对齐了指令①的多条要求**（尤其是 `logic_ledger` 假设监控和 `/api/decisions/swing` 的 AI 分层雏形），这不是"贴标签"，是真实的工程投入。但截至审查的 commit，这些新能力**大部分还是"造好了但没有接进主决策回路和主 UI"**——旧的打板向决策卡（`DecisionVerdictCard.tsx`）、旧的 ReAct Agent 工具表（`agentTools.ts`）、旧的深度调研后端（`server/routes/research.js` 依赖 Windows 本地 Python 脚本）都还原封不动地占据着用户实际会看到的主路径。所以最终使用体验上，**普通用户打开系统，大概率还是看到"游资打板信息终端"，只有钻进"波段作战室"这个新增页签才能看到真正的波段/产业链能力**——这就是当前最大的问题：**新地基没有取代旧门面**。

## 二、指令①"验收基线五问"逐条复核

> 指令①原文：重构完成后系统必须能"秒回"以下 5 个问题，回答不出来就是没做到位。

### 问题①："这只票现在处于哪条产业链的什么位置？这条链最近发生了什么变化？"
**状态：部分完成**
- 证据（完成部分）：`GET /api/chain/context?code=xxxxxx`（`server/routes/chain.js`）会先查 `industry_chain_node_stock`（`chainDb.js:getChainDbContext`），返回 `chainName/nodeName/upstream/downstream/exposurePct/signals`，且 `exposurePct` 来自东财 F10 主营构成真实数据，非编造。
- 证据（未完成部分）：链库仍只有 10 条（`src/shared/transmission-chain.js`），AI 算力/机器人/创新药/军工/消费出海等指令①3.3 节明确要求扩容的方向仍未覆盖；且"这条链最近发生了什么变化"这一半——`industry_chain_signal`/`industry_chain_event`（传导事件表）在 `chainDb.js` 中只有信号查询（`SELECT ... FROM industry_chain_signal`），**没有找到"传导推理 Agent"生成 `industry_chain_event` 的代码**（指令①5.1节②），即"链变化的推理结论"这一半没有闭环。

### 问题②："如果我现在买，理由是什么？打算拿多久？什么情况下我应该认输离场？"
**状态：部分完成（能力已具备，但未接入主决策卡）**
- 证据（完成部分）：`server/routes/decisions.js` 的 `POST /api/decisions/swing` 明确要求 DeepSeek 输出：
  ```json
  {"verdict":"...", "score":0-100, "buyPoint":"...", "stopLossPct":5, "targetPct":15,
   "positionRange":[10,20], "holdingHorizonDays":20, "reviewCycleDays":20,
   "reasons":["证据链"], "blocks":["风险"],
   "evidenceChain":[{"step":"产业链","evidence":"引用具体数据"}],
   "invalidationConditions":["假设失效条件"], "signal":"一句话"}
  ```
  这与指令①1.2节的"波段投研决策卡"字段规格高度吻合，且 `thinking:true, maxTokens:8000`，调用前已聚合行情K线、产业链上下文、研报/机构调研/股东户数/解禁数据、新闻公告——是本轮审查发现的**最重要正向证据**。
- 证据（未完成部分）：抽查主决策卡组件 `src/components/DecisionVerdictCard.tsx`，其数据源仍是旧的 `runConsensus/aiAgent`（打板五件套 ReAct），**没有发现对 `/api/decisions/swing` 的调用**。也就是说这张"真正像波段投研决策卡的卡"目前只存在于后端 API 层，前端主界面用户看不到。是否有其他组件（如 `BattlePlan.tsx`，26KB，未逐行抽查完）消费该接口——**无法验证**（受限于单文件抓取长度，未能读完全文，标注为"无法验证"而非"未完成"）。

### 问题③："上周你（AI）说的判断，现在验证得怎么样了？"
**状态：部分完成**
- 证据（完成部分）：`src/lib/decisionAttribution.ts` 的 `computePostHitrate` 会拿 `decision_post`（人类拍板记录）配对 `decision_log`（AI/规则裁决），回填真实 T+5 盈亏，分 `ai/rule/degraded` 三桶统计命中率；`decision_post` 表新增了 `pnl_t20`、`pnl_t60` 字段（`db-migrations.js`），说明团队已经在向"周/季度级复盘"方向扩展。
- 证据（未完成部分）：`computePostHitrate` 的主逻辑和 UI 展示（`DecisionVerdictCard.tsx` 中"历史对账（近14日）"）**仍只使用 T+5 桶**，没有发现 T+20/T+60 桶的计算函数或 UI 展示——字段加了，但统计/展示逻辑没跟上，**当前用户看不到"周/月级别"的命中率**。
- "系统主动追踪、到期自动复盘"（指令①原文强调"不是等你来问"）——`logic_ledger.next_review_at` 字段已存在，但**没有找到读取该字段并主动触发复盘/推送的 cron 任务**（`server/cron/` 目录内容本轮未逐一抽查完，标注"无法验证"）。

### 问题④："这条产业链/这只票的关键假设有没有被证伪？"
**状态：已完成（本轮最扎实的一项）**
- 证据：`logic_ledger` 表 `status` 字段枚举 `验证中/已兑现/已证伪/已离场`，配合 `invalidation_conditions`（JSONB）、`break_line`（破位线）；前端 `SwingWarRoom.tsx` 的"持仓逻辑台账"组件（`LogicLedgerPanel`）允许用户录入"买入逻辑+催化验证点+破位线"，并调用 `checkAllLedgerAlerts`（`src/shared/logic-ledger.js`，服务端/前端同源）产出四类提醒：`break_line`（破位）/`catalyst_due`（催化到期）/`board_ebb`（板块退潮）/`logic_falsified`（逻辑证伪）。这是一个真实、可运行、双端同构的假设监控机制。
- 局限：目前是**用户手动录入**逻辑卡片，不是"AI 自动为每次买入建议生成假设并自动监控"——即指令①要求的"AI 生成 → 自动挂载 → 自动监控"没有完全自动化，仍需人工建卡。

### 问题⑤："你（AI）学到我的哪些偏好/教训了？"
**状态：部分完成**
- 证据（完成部分）：`DecisionVerdictCard.tsx` 中能看到 `loadUserProfile()/profileToPrompt()` 被调用并在 UI 展示"👤 用户画像：..."一行，说明画像**至少在旧的打板决策卡里已经真实读取并展示**（这与报告①"AI已参考用户画像是假的"的说法相比是明确的改善）。`feedbackPenalty.js` 也证明"用户说AI判断不准确"这一反馈确实会被聚合并用于**实际扣分/缩仓**（`applyDecisionPenalty`），不是摆设。
- 证据（未完成部分）：在新的 `/api/decisions/swing`（AI波段综合研判）prompt 构造（`llmSwingDecision`）中，**没有看到用户画像被注入 prompt**——也就是说"新的、更重要的波段决策入口"反而还没用上"旧的、已经验证有效的画像能力"，两条线又没对齐。`behaviorCoach.detectBehaviorBias` 检测出的行为偏差（处置效应/追高/频繁交易）目前只用于"纪律教练"面板文案展示，**未发现回写用户画像或影响后续决策仓位**的代码路径。

**五问综合结论**：5 问里，1 问（④ 假设证伪）已经做到"能拿真实数据回答"；2 问（① 产业链定位、② 买卖理由与周期）具备了后端能力但没打通到用户能看到的主路径；2 问（③ 历史验证、⑤ 画像学习）有真实雏形但统计口径/接入范围不完整。**没有一问能达到指令①"连续问一遍，全部给出有数据支撑的回答"这一验收线**，因为主 UI 决策卡还是旧的。

## 五、本轮审查发现的新风险（第一轮报告未提及）

1. **深度调研后端存在生产可用性硬伤**：`server/routes/research.js` 通过 `execFile` 调用本机 Python 脚本，路径写死为 `C:/Python312/python.exe` 与 `C:/Users/Administrator/.workbuddy/skills/...`。这意味着"个股深度调研"功能**只能在开发者本人的 Windows 机器上运行**，一旦部署到服务器/容器/CI 环境，该功能会 100% 失败。这是一个比"思考深度不够"更根本的可用性问题，指令①未覆盖，建议列入第二轮 P0。
2. **新旧两套决策卡长期并存且互不感知**：`DecisionVerdictCard.tsx`（打板五支柱+游资战术）与 `/api/decisions/swing`（波段AI综合研判）是两条完全独立的代码路径，没有共享 UI、没有共享 prompt 里的用户画像、没有共享反馈回写目标表（前者写 `decision_log`/`decision_post`，后者的落库路径本轮未查到，**无法验证**其结果是否进入同一张 `decision_post`/`logic_ledger`）。如果不尽快合并，会出现"两套 AI 各说各话"的风险。
3. **`industry_chain_event`（传导事件表，指令①5.1节②的核心产出）未落地**：这意味着"一次产业链推理，多只股票复用"的降本设计没有实现，如果后续把 `/api/decisions/swing` 的调用量做大，token 成本会线性增长而不是被推理复用摊薄。

## 七、结论重申

第二轮审查的核心判断：**这不再是"纯粹的忽悠"，团队在 v9.138~v9.144 系列投入了真实的、方向正确的工程量**（产业链数据库化、波段专用决策模型、假设监控台账、AI 综合研判接口、反馈闭环写入端全部从"报告①里说的0"变成了"及格线附近的真实代码"）。但**系统性验收仍然不通过**，原因高度集中于一点：**新能力大多是"侧线新增"，没有"替换/接管"用户实际会走的主路径**（主决策卡、主 AI Agent 工具表、深度调研入口都还是旧的）。第二轮修改指令的核心任务不再是"从0到1造能力"，而是"**把已经造好的能力，接管/替换掉旧的主路径**"，这是一个更聚焦、工作量也更可控的任务。
