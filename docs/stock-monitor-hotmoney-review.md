## 0. 一句话结论

**这是一套"数据宅男"造的监控台，不是"操盘手"用的作战室。** 代码质量、字段口径、异常兜底做得相当扎实（比很多收费软件还认真），但产品的"骨架"是按"看数据"设计的，不是按"做决策—扣扳机—管仓位"设计的。游资要的三样东西——**竞价现场感、盘中反应速度、纪律约束**——这套系统目前基本没有。这不是加几个组件就能补的，是需要重新想清楚"这东西到底在人的交易流程里的哪一环起作用"。

## 一、总体印象：底子很好，但方向偏了

### 值得肯定的部分（不吝啬表扬）
1. **龙虎榜模块**做得有深度：席位画像、行为模式打标（格局派/波段派/砸盘派/接力派）、买卖主导派 5 维评分、合力/独食信号、游资连续动作追踪——这已经超出大多数同类开源项目的水平。
2. **涨停梯队 / 题材梯队**：按行业分组、龙一龙二龙三识别、断板预警、早盘先锋标记，思路是对的。
3. **一票否决风控清单**（VETO）：主力流出+散户流入、换手率超阈值、解禁临近、关键词扫描减持/立案/业绩雷——这是少见的"反向止损意识"，说明作者理解游资最怕什么。
4. 数据口径的较真程度很高（比如涨跌家数改用交易所官方字段而非翻页统计、涨跌停幅度按 2026 年新规重新判断、字段解析失败返回 null 而非静默为 0）——工程素质在线。

### 但是——核心问题：产品定位模糊
现在的系统同时想做：全市场监控 + 资金面分析 + 龙虎榜复盘 + 题材追踪 + 个股诊股 + AI 督导 + 避坑指南，**七合一但没有主次**。游资的操作节奏是"9:15 竞价 → 9:25 开盘抢筹 → 盘中跟随/加仓/离场 → 收盘复盘 → 龙虎榜验证"，是一条**时间轴上的动作链**，而现在的系统是"五个 Tab + 若干卡片"的**平铺陈列**，用户要自己在脑子里把它们拼回那条时间轴。这是最需要推倒重来的地方。

## 三、致命短板逐项分析

### 3.1 数据主权缺失：全站靠 `localStorage`，等于"每天失忆的看盘助手"
**现象**：涨停快照（`ztSnapshot`）、龙虎榜席位台账、人气榜昨日对比、自选股列表等所有需要"跨日积累"才有价值的数据，全部写在浏览器本地存储里。GitHub Pages 是纯静态托管，没有后端、没有数据库、没有定时任务。

**为什么游资在意**：游资打法的核心资产之一就是"对某个游资营业部长期行为的记忆"——比如某席位历史上做过的票、胜率、T+1 表现。这套系统的"席位画像"模块设计理念是对的，但**数据积累完全绑定在某一台电脑的某一个浏览器上**：换个电脑看盘＝画像清零；清一次缓存＝断板预警失效；只要某天没人恰好打开这个页面，那天的收盘快照就永远丢失，形成"数据空洞日"，后续所有依赖"昨日快照"的功能（断板预警、连续动作、席位胜率）都会因为空洞日而产生误判或直接失效。

**修改方向**：
- 引入轻量云端存储（如 Cloudflare D1/KV、Supabase、或自建一个极简的 Serverless 接口），把"涨停快照、龙虎榜台账、席位画像、自选股、复盘日志"迁移为云端存储，`localStorage` 仅作离线缓存兜底。
- 用定时任务（GitHub Actions 定时 cron 或 Cloudflare Worker Cron Trigger）在每个交易日收盘后（15:30 后）自动抓取并写入云端快照，不再依赖"有没有人凑巧开了网页"。
- 给用户提供"数据云同步"开关和登录态（哪怕是最简单的邀请码/设备码机制），让同一个人换设备也能看到连续的历史。

### 3.2 龙虎榜是"事后诸葛亮"，产品里却没有标注这一点
**现象**：龙虎榜数据源自东方财富数据中心接口，天然是**收盘后／隔天**才更新，这在 A 股是行业常识。但系统的 UI 文案（"龙虎榜复盘"这个 Tab 名字算是诚实的）和整体呈现风格，容易让不熟悉规则的用户误以为可以"盘中看龙虎榜决策"。

**为什么游资在意**：真正的游资操作节奏是"竞价定生死"——9:15-9:25 集合竞价阶段的委托挂单、竞价成交量、竞价换手率、是否有大单托价/砸价，这才是当天能不能进场的第一手判断依据。等龙虎榜数据出来，行情早就走完了，只能用来**验证**昨天的判断、给今天的操作提供"信誉背书"参考（比如某票被知名游资连续买入，值得继续跟）。

**现状问题**：整个系统里**没有集合竞价监控模块**，这是全套系统里最大的功能空洞，等于把游资交易流程里最关键的"开盘前 10 分钟"完全跳过了。

**修改方向**：
- 新增"竞价台"模块：抓取 9:15 起的实时竞价数据（价格、竞价量、竞价换手率、相对昨日收盘涨幅），做涨停池个股的"竞价强度排行"（重点关注是否有票在竞价阶段就封住涨停或呈现大笔买单）。
- 在龙虎榜相关模块的标题/说明文字中，更醒目地标注"数据更新时点：交易日收盘后 16:00-18:00 陆续更新，仅用于复盘与次日操作参考，不可用于盘中实时决策"，避免误导。

---

### 3.3 "主力资金流"这个指标本身对游资参考价值有限，但系统里权重给得偏高
**现象**：全站大量使用东方财富的"超大单/大单/中单/小单净流入"（即所谓"主力资金"）作为核心指标，贯穿市场概览、资金结构、个股监控、板块排名等几乎所有模块。

**为什么游资在意**：这套分类本质上只是**按单笔委托金额门槛**做的粗暴分层（比如成交额超过多少万算"大单"），并不能真正区分"是机构长线资金、游资短线资金、还是大户散户"。游资本身操作时经常会**主动拆单**（把一个大单拆成多个中小单委托，规避被系统识别为"大单出货/进货"），这套"资金流"指标在游资操作面前经常是失真甚至反向的。业内很多老手对这套指标的评价是"仅供参考，别当真"。

**现状问题**：系统里"资金结构""市场情绪温度计"公式（`upRatio×40 + limitScore×1.3 + avgPctScore×0.8 + indexScore + 20`）虽然额外引入了涨停家数、指数涨跌等更硬的指标做修正，但个股监控（`StockWatchlist`）里的"一票否决"逻辑仍然把"主力流出+散户流入"作为第一条硬规则，权重偏重。

**修改方向**：
- 在所有展示"主力资金流"的地方，加一条**局限性说明**（可折叠的 tooltip 或脚注）："该指标按委托金额门槛统计，无法识别拆单/对倒等操作，仅作参考，不建议单独作为买卖依据"。
- 调低资金流指标在"一票否决"和"健康度评分"中的权重，提升更难被操纵的指标权重：换手率、量比、封单量／流通市值比、龙虎榜净买入、盘口买一档撤单频率（如可获取）。
- 增加"资金流与股价背离"专项提示（比如资金流转正但股价滞涨、或资金流转负但股价抗跌），这种背离本身比资金流绝对值更有信息量。

### 3.4 情绪周期判断停留在"温度计"，没有"退潮预警"复合模型
**现象**：现有"情绪温度计"是一个静态加权公式，产出一个 0-100 的数字；涨停池、炸板率、连板梯队等数据都已经抓取到位，但**没有把这些数据组合成一个"情绪所处周期阶段"的判断**（启动期/主升期/分歧期/退潮期/冰点期）。

**为什么游资在意**：游资交易的本质是"赌情绪周期的位置"——冰点期敢左侧埋伏，主升期敢右侧追高，退潮期必须清仓离场。判断错周期阶段，其他所有分析都没有意义。行业里常用的复合信号包括：连续 N 日涨停家数环比变化、最高板高度是否创出新高后开始滞涨、炸板率是否连续攀升、涨停股次日溢价率是否持续走低、两融余额是否见顶回落、题材股波动率是否放大。

**现状问题**：这些原始数据（炸板率、连板高度、两融数据、题材梯队）在系统里都已经分散存在，但**没有一个统一的"周期判断仪表盘"把它们组合起来给出结论**，用户仍然需要自己在脑子里拼图。

**修改方向**：
- 新增"情绪周期雷达"模块，把温度计升级为"温度计 2.0"：综合连板高度变化、涨停总数环比、炸板率趋势（近 3 日）、涨停次日溢价率（用已有的席位/龙虎榜历史回填数据）、两融余额变化率，给出五档周期判断（启动/主升/分歧/退潮/冰点）及配套操作建议基调（可以进攻/控制仓位/清仓观望/左侧试仓）。
- 在周期判断旁边强制展示"支撑该判断的 3-5 项具体数据"，避免变成又一个黑箱评分。

---

### 3.5 只有信息，没有约束：仓位管理和交易纪律模块完全缺失
**现象**：系统对"选股""判断"投入了大量精力，但对"买多少、几成仓、止损位设在哪、今天总敞口多大"这类**纪律层面的东西完全没有涉及**。唯一接近风控的是个股监控里的"一票否决"清单。

**为什么游资在意**：游资圈公认"选股是徒弟活，仓位管理是师傅活"。真正决定长期生存的不是选中了多少只票，而是**单票仓位上限、总仓位曝光、连续亏损后是否强制降低操作频率**这类纪律。没有这层约束，再好的信号系统也只是"看得爽、亏得惨"。

**修改方向**：
- 新增"仓位与纪律面板"：允许用户录入当前总资金、已用仓位、单票仓位占比；对超过预设单票仓位上限（如 30%）、总仓位上限、当日新开仓次数过多等情况做实时提醒。
- 结合已有的一票否决清单，做"止损位建议计算器"（例如按 ATR 或近期支撑位、板块平均回撤幅度给出参考止损价，而非固定百分比）。
- 加入"连续亏损冷静期"提醒：如果用户在复盘日志中连续记录 N 次亏损交易，弹出"建议降低操作频率/仓位"的强提示（呼应避坑指南的理念，但做成主动干预而非被动阅读）。

### 3.6 单一数据源 + 纯前端直连，稳定性是纸糊的
**现象**：全站所有数据都来自东方财富公开接口（push2 / push2ex / push2his / datacenter-web / np-anotice-stock 等），通过 JSONP 或裸 fetch 跨域直连，没有中间代理层。README 里也坦承"人气榜接口 POST + CORS 可能受限""北向资金接口自 2024 年 8 月起间歇性断供"。

**为什么游资在意**：盘中最怕的就是"该看的时候看不到"。东方财富对高频访问有限流策略（代码里已经用了并发队列规避 502/限流），一旦东财单方面调整接口签名、封锁某些 IP 段、或对 GitHub Pages 这类公共域名来源做屏蔽，整个系统会瞬间"全灭"，且由于是纯前端直连，没有服务端可以做熔断降级或切换备用源。

**修改方向**：
- 搭建一层轻量反向代理（Cloudflare Worker 或 Vercel Edge Function 均可，成本极低），把所有对东财的请求经代理转发：一是解决人气榜等 POST 接口的 CORS 限制，二是可以在代理层做统一缓存（比如 5-10 秒缓存同一接口的重复请求，降低对源站的压力，同时提升多用户访问时的响应速度），三是为未来接入备用数据源留出切换点。
- 接入至少一个备用行情源（如新浪财经、腾讯证券公开行情接口）作为东财接口失败时的降级方案，至少保证"指数、涨跌家数、个股行情"这类核心数据不至于完全空白。
- 把 `apiHealth` 遥测数据（已有 `recordApiCall`）做成一个"接口健康总览"页面，公开展示各接口近期成功率/延迟，既方便自己排查，也增加用户对数据可信度的信任感。

### 3.7 移动化和主动推送几乎为零，而游资经常不在电脑前
**现象**：系统有站内声音提示和浏览器 Notification API 通知，但这两者**都要求浏览器标签页保持打开**，一旦用户切到别的应用、锁屏、或者根本没开电脑，所有预警都收不到。没有 PWA 离线能力，没有响应式移动布局的针对性优化（大量密集表格在手机上体验会很差）。

**为什么游资在意**：游资很多时候是"人不在电脑前但要盯盘"的状态（出门吃饭、开会间隙），关键提醒（比如自选股触发一票否决、封单被砸开板、龙虎榜首次出现关注已久的席位）必须能突破"浏览器标签页存活"这个限制，直接推到手机上。

**修改方向**：
- 接入至少一种轻量外部推送渠道（Server 酱、企业微信机器人 Webhook、Bark、或 Telegram Bot 任选其一，实现成本都很低），把"critical 级别"预警（一票否决触发、涨停开板、龙虎榜命中自选股）同步推送到用户手机。
- 做移动优先的响应式改造：核心 Tab（驾驶舱、资金主线、个股雷达）在窄屏下改为单列卡片流，密集表格改为可横向滑动或转为"要点摘要+展开详情"的折叠结构。
- 补充 PWA 配置（manifest + service worker），支持"添加到主屏幕"，即使离线也能看到最近一次缓存的数据，减少纯网页在弱网环境下的白屏体验。

### 3.8 复盘缺乏"结构化留痕"，无法沉淀成长期打法体系
**现象**：系统里有"避坑指南""AI 督导""每周教练"这类偏说教型的静态内容模块，但**没有让用户把每天的操作和思考记录下来**的结构化复盘工具。30 天资金快照、龙虎榜台账都是系统自动生成的"客观数据"，缺少"主观决策记录"这一环。

**为什么游资在意**：游资的成长曲线几乎全靠"复盘笔记"喂出来的——今天的主线是什么、龙头是谁、我为什么打了这一板、为什么没接、事后看对错在哪。没有结构化记录，AI 督导给出的建议也只能是泛泛而谈，无法针对"这个人过去反复踩的坑"做个性化提醒。

**修改方向**：
- 新增"每日复盘卡片"功能：交易日收盘后引导用户用固定模板快速填写（今日主线/今日龙头/我参与的票/盈亏/操作反思，可选1-2句话），存入云端（结合 3.1 的持久化改造），沉淀为可检索、可按月/按题材统计的复盘库。
- 把 AI 督导的分析输入源，从"当前市场快照"扩展为"结合该用户历史复盘记录"，让督导建议具备针对性（例如系统发现该用户过去 5 次追高一字板都亏损，本次同类情形出现时给出针对性提醒，而非通用话术）。

### 3.9 UI 信息密度过载，缺乏"分时段皮肤"
**现象**：目前只有 5 个顶部 Tab（驾驶舱/资金主线/个股雷达/龙虎榜复盘/消息面），却要承载 30+ 个功能组件，很多页面内信息高度密集（表格嵌套表格、展开又展开）。这种设计更适合"周末花半小时慢慢研究"，不适合"盘中 3 秒扫一眼"。

**为什么游资在意**：盘中决策要求的是"3 秒内看懂关键结论"，不是"5 分钟慢慢读数据"。现在的信息架构没有区分"盘前准备/盘中盯盘/盘后复盘"这三种完全不同的使用场景，导致每个场景都用同一套密集布局，效率打折。

**修改方向**：
- 按交易时间轴重新组织导航结构，建议改为：**盘前竞价 → 盘中作战 → 盘后复盘 → 资金体检 → 消息情报** 五个板块（在保留现有功能组件的前提下重新归类，而非推倒重做）。
- 为"盘中作战"场景单独设计一个高度精简的"极简盯盘卡"视图：只展示情绪周期结论、自选股预警红点、当前主线龙头 3-5 只，其余细节收进"查看详情"，作为默认首屏；现有的深度分析页面保留作为"深度复盘模式"，通过一个明显的模式切换按钮区分。

### 3.10 合规话术风险：措辞偏"荐股"，需要收敛
**现象**：部分模块使用了"操作建议""一句话操作建议""主导派与操作建议"这类直接给出操作指令式的文案，虽然页面底部有免责声明，但核心交互文案的语气偏强指令性。

**为什么游资在意**：这不是"胆小怕事"，是行业常识——任何公开发布、他人可访问的工具，一旦文案呈现为"明确的买卖操作指令"，在国内监管口径下容易被认定为"荐股"或"投资建议"，个人开发者独立承担这类合规风险性价比很低，尤其项目已经公开部署在 GitHub Pages 且写了详细 README。

**修改方向**：
- 把"操作建议"类文案统一改写为"信号强度参考""历史统计规律"式的中性表达（例如把"建议买入"改为"该形态历史上出现 N 次，T+1 上涨概率 X%，仅供参考"），弱化指令语气，强化"用户自主判断"的呈现方式。
- 在每个给出"倾向性结论"的模块（BattlePlan 主线排序、AI 督导、健康度评分）旁边增加统一的小字免责标注，而不只是页面最底部一行大字免责声明。
- 检查 AI 督导对话功能的系统提示词，确保 AI 输出也遵循"陈述数据事实 + 历史统计，不做绝对化操作指令"的原则。

## 五、UI/UX 与信息架构重构建议

1. **按交易时间轴重组导航**：盘前竞价 → 盘中作战 → 盘后复盘 → 资金体检 → 消息情报，替换现有"驾驶舱/资金主线/个股雷达/龙虎榜复盘/消息面"的平铺式分类，让用户在对应时间段自然打开对应板块。
2. **"极简盯盘"与"深度复盘"双皮肤切换**：盘中默认展示高度精简的结论卡片（情绪周期结论、自选股红点预警、当日主线龙头），点击可展开进入现有的详细分析视图，避免每次打开都要面对信息过载。
3. **统一"数据时效标签"组件**：在所有卡片/模块标题旁统一加一个小标签，明确标注该数据是"实时（≤1分钟）""准实时（约5-15分钟延迟）"还是"T+1复盘数据"，这是重建用户信任、避免误用最低成本的改动。
4. **弱指令化的视觉语言**：减少红/绿强对比的"操作建议"大字号呈现，改用更克制的中性配色和"参考信息"式排版，配合第 3.10 条的文案调整同步进行。
5. **关键预警的"离场路径"**：任何触发一票否决/风险警示的地方，除了展示"为什么危险"，也要给出"接下来该做什么"的引导（例如链接到止损位计算器、复盘日志快速记录入口），把信息真正转化为动作。

## 六、技术架构优化建议

1. **代理层**：新增一层边缘代理（Cloudflare Worker / Vercel Edge Function），统一转发东财等第三方接口请求，附带短 TTL 缓存（5-10 秒级）与统一限流策略，替代目前纯前端直连 + 客户端并发队列的方案。
2. **持久化层**：引入轻量云数据库（Cloudflare D1/KV、Supabase 等成本可控的方案），迁移涨停快照、龙虎榜台账、席位画像、自选股、复盘日志。`localStorage` 降级为离线缓存层，不再是唯一数据源。
3. **定时任务**：用 GitHub Actions 的 `schedule` 触发器或 Worker 的 Cron Trigger，在每个交易日收盘后固定时间自动抓取并写入云端快照，摆脱"必须有人打开网页才会积累数据"的被动模式。
4. **备用数据源**：至少为"指数行情、涨跌家数、个股实时价"这类核心字段接入一个备用源（新浪财经或腾讯证券公开接口），在东财主源连续失败时自动降级切换，并在 UI 上标注"当前使用备用数据源，部分字段可能缺失"。
5. **监控可视化**：把已有的 `apiHealth` 遥测数据做成一个独立的"系统状态"页面，展示各接口最近成功率、平均延迟、最近一次失败时间，既用于自查，也增强用户信任。
6. **推送通道**：新增一个轻量通知网关（可以直接用 Server 酱 / 企业微信机器人 Webhook 这类零成本方案），把 `alertBus` 里 critical 级别事件转发到外部渠道，而不仅仅停留在站内提示音和浏览器 Notification。

## 七、合规与文案规范建议

1. 全站排查并改写所有"操作建议""建议买入/卖出/加仓/减仓"等指令式措辞，统一替换为"信号强度""历史统计规律""仅供参考"等中性表达。

## 九、给 DeepSeek V4 Flash 的逐条可执行指令清单

> 说明：以下指令按模块分类编号，每条描述"要做什么、为什么、验收标准"，不含具体代码。请按 P0→P1→P2→P3 顺序逐条执行，每完成一条做一次构建验证。

- **T2**：在所有产出倾向性结论的卡片组件标题栏旁，统一新增一个可复用的小字免责标签组件（如 `<DisclaimerTag />`），内容为"仅供参考，不构成投资建议"，替代目前只在页面底部集中声明的方式。
- **T3**：为 `AlertBanner`/`WeeklyCoach`/`Playbook`（避坑指南相关模块）增加"首次访问强制展示一次"的逻辑（可用 localStorage 记录是否已读），确保风险教育内容被真正看到而非被忽略。
- **T4**：检查 AI 督导（`IntelligenceDrawer.tsx` 及其调用的 `lib/ai.ts`）的系统提示词（system prompt），加入明确约束："只做数据陈述和历史统计分析，不输出绝对化的买卖指令，所有结论需附带'仅供参考'"。

### （二）数据时效透明度类
- **U1**：新建一个统一的"数据时效标签"小组件，接受"实时/准实时(约X分钟延迟)/T+1复盘"三种状态参数，样式为醒目但不刺眼的小徽标。
- **U2**：在 `DragonTiger.tsx`（龙虎榜）、`DarkPool.tsx`（明暗盘）顶部说明文字处，接入 U1 组件并标注真实更新时点（如"龙虎榜数据于交易日收盘后 16:00 起陆续更新，仅用于复盘及次日参考，不可用于盘中实时决策"）。
- **U3**：在 `api.ts` 中为每类数据源（push2 实时行情 / datacenter-web 龙虎榜 / push2ex 涨停池）维护一个"预期延迟"元数据映射，供 U1 组件统一取用，避免各组件各写各的文案导致口径不一致。

### （三）竞价监控（P0 核心新功能）
- **F1**：新增"竞价台"数据获取函数（参考东方财富个股/涨停池相关接口是否提供集合竞价字段，如无法直接获取则退而求其次，用开盘后第一笔实时数据 + 涨停池的"首封时间"字段做近似的"早盘强度"替代指标），产出字段至少包含：代码、名称、竞价价、竞价涨幅、竞价量（或早盘量比）。
- **F2**：新增"竞价台"组件，展示自选股 + 昨日涨停股在竞价阶段（或开盘前 5 分钟）的强度排行，按竞价涨幅/量比降序排列，高亮"竞价即封板"和"竞价大幅低开"两类极端情形。
- **F3**：将"竞价台"接入 `TopNav.tsx` 导航体系（按第五节建议的时间轴式导航重组，放在"盘前"分组下）。

### （四）云端持久化（P0/P1 地基类）
- **D1**：评估并选定一个轻量后端方案（Cloudflare Worker + KV/D1，或 Supabase 免费额度），设计最小化的数据表结构，覆盖：涨停快照（`ztSnapshot`）、龙虎榜席位台账（`seatProfiles`相关）、人气榜昨日对比、自选股列表、复盘日志。

- **D3**：新增一个极简的设备/用户标识机制（如邀请码或简单的本地生成 + 手动同步码），支持同一用户换设备后能够拉取到之前云端保存的历史数据。
- **D4**：新增一个定时任务（GitHub Actions workflow 的 `schedule` 触发，或云函数的 Cron Trigger），在交易日收盘后固定时间点自动请求关键接口并写入云端快照，不再依赖"用户凑巧打开页面"。

### （五）情绪周期雷达
- **F4**：新增 `emotionCycle` 计算模块，综合近 3-5 日的涨停总数环比、最高连板高度变化、炸板率趋势、涨停次日溢价率（复用已有龙虎榜/涨停回填数据）、两融余额变化率（复用 `MarginPanel` 数据源），输出五档周期标签（启动/主升/分歧/退潮/冰点）及对应的仓位基调建议（中性表达，参考 T1 要求）。

- **F10**：新增"每日复盘"录入组件，在交易日收盘后（可结合 `getCurrentSession` 判断当前时段）主动引导用户填写，支持按月/按题材检索历史复盘记录。
- **F11**：将复盘日志数据接入 AI 督导（`lib/ai.ts` 调用逻辑），让 AI 分析时能够引用用户历史复盘中反复出现的问题模式，生成个性化提醒（同样遵循 T4 的中性表达约束）。

### （八）外部推送
- **F12**：新增通知网关封装（对接 Server 酱 或 企业微信机器人 Webhook 二选一优先实现），在 `SettingsModal.tsx` 中新增配置入口，允许用户填入自己的推送密钥/Webhook 地址。
- **F13**：将 `lib/alertBus.ts` 中 `severity === "critical"` 的事件（一票否决触发、涨停开板、自选股命中龙虎榜等）同步调用 F12 的推送网关，实现站外强提醒。

### （九）代理层与稳定性
- **P-1**：搭建边缘代理服务（独立于本前端项目部署），统一转发 `api.ts` 中所有对东方财富域名的请求，代理层附加短 TTL 缓存与限流。
- **P-2**：把前端 `api.ts` 中直连东财域名的 URL 拼接逻辑，替换为指向自建代理的请求（保留原始参数结构，降低改造成本）。
- **P-3**：为核心行情字段（指数、涨跌家数、个股实时价）接入一个备用数据源，在主源连续失败 N 次后自动切换，并在界面显著位置提示"当前使用备用数据源"。
- **P-4**：新增"系统状态"页面，展示 `lib/apiHealth.ts` 已记录的各接口成功率、平均延迟、最近失败时间，供自查与增强用户信任。

- **C2**：新增"极简盯盘"视图作为盘中时段的默认首屏（可结合 `getCurrentSession` 自动判断并推荐切换），内容仅包含：情绪周期结论卡（F5）、自选股预警红点摘要、当前主线龙头 Top3-5，并提供"查看完整深度分析"入口跳转回现有详细视图。

## 十、附录：术语与本报告核心判断依据对照表

| 术语 | 含义 | 与本报告结论的关系 |
|---|---|---|
| 竞价现场感 | 集合竞价阶段（9:15-9:25）的挂单、成交、撤单动态 | 游资决策的第一现场，本报告认定为当前系统最大功能空白（F1-F3） |
| 主力资金流 | 东财按委托金额门槛统计的大单/中单/小单净流入 | 并非真正的机构/游资资金识别指标，本报告建议降权并加局限性说明（3.3） |
| 一票否决 | 系统对个股设置的强制风险排除规则 | 已有实现思路正确，建议结合仓位/止损建议形成完整闭环（3.5, F6-F8） |
| 退潮预警 | 判断市场炒作情绪由高潮转向衰退的复合信号组合 | 当前系统零件齐全但未组装成结论，是本报告重点新增建议（F4-F5） |
| 数据主权 | 数据是否掌握在系统/用户手中而非依赖单一浏览器缓存 | 本报告认定为当前架构最大隐患，建议优先解决（D1-D4） |
| 强指令性文案 | "建议买入/卖出"等直接给出操作指令的表达方式 | 存在合规风险，建议全面替换为中性统计式表达（T1-T4） |
